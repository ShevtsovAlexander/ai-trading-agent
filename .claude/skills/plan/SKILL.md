# Фаза: PLAN

Спроектируй решение под активный тикет на основе research.

## Шаги
1. Тикет из `docs/aidd/.active_ticket`.
2. PRD `docs/aidd/prd/<ticket>.prd.md`, research `docs/aidd/research/<ticket>.md`.
3. `docs/DECISIONS.md` — не противоречь прошлым решениям.
4. `docs/VISION.md` — принципы и границы.

## Железные правила
1. **Опирайся на research.** Каждое решение — со ссылкой на факт (`файл:строка`).
   Research не покрыл нужное — верни на доуточнение, не достраивай сам.
2. **Следуй паттернам проекта.** Не изобретай стиль если есть устоявшийся.
   Ссылайся на пример из research.
3. **Задачи маленькие и проверяемые.** Каждая: один шаг + конкретный критерий
   готовности (не «улучшить», а «метод Y возвращает Z»).
4. **Оракул на каждую задачу с логикой.** Чем проверять ПРАВДУ: эталонная либа /
   реальные данные / известный ответ / ревью человека. Нет оракула → тест не писать
   (будет false-green), пометь это явно.
5. **Не пиши код.** Только план и tasklist.

## Выход — два файла

`docs/aidd/plan/<ticket>.md`:
```markdown
# План: <TICKET>
## Подход
## Компоненты
| Файл | Новый/Правка | Что делает | Паттерн из research (ссылка) |
## Контракты (сигнатуры, типы, форматы)
## Поток данных
## Trade-offs (что выбрано, что отвергнуто, почему)
## Риски (ссылки на research)
```

`docs/aidd/tasklist/<ticket>.md`:
```markdown
# Tasklist: <TICKET>
- [ ] **TASK-N.1: <название>**
  <что сделать>
  - Критерий готовности: <проверяемо>
  - Оракул: <эталон / данные / ревью / нет — почему>
```

## Финал
Покажи план + tasklist, подсвети trade-offs, остановись. Не реализуй без согласования.
