# План: TASK-0001 — миграция торгового бота в информационный дашборд

Опора: `docs/aidd/research/TASK-0001.md` (все ссылки `файл:строка` — оттуда),
PRD `docs/aidd/prd/TASK-0001.prd.md`, границы `docs/VISION.md`.

## Подход

Демонтаж идёт **снизу вверх и по слоям связности**, а не «по папкам».
Порядок продиктован двумя фактами из research:

1. **Сбор цен спрятан внутри торгового анализа.** `PriceSnapshot` пишется в
   `price.service.ts:41,56`, а вызывает это cron через `analyze()`
   (`price.scheduler.ts:25`). Значит нельзя «удалить analyze» — из него
   нужно **вынуть** вердикты, оставив сбор фактов на месте.
2. **Схема и код должны двигаться вместе.** Вердиктные поля NOT NULL
   (`schema.prisma:38-43`): убрать их из `create()` без миграции = падение
   на первом же cron-цикле. Поэтому «код вердиктов» и «DROP COLUMN» —
   одна задача, а не две.

Отсюда **шесть** шагов бэкенда: снять изолированное (wallet/position) →
снести мёртвые таблицы → снять write-only колонки снимка цены → вырезать
вердикты вместе с колонками → переименовать → переделать AI-слой. Затем
фронт четырьмя шагами, **упорядоченными так, чтобы `npx tsc -b` оставался
зелёным после каждого** (сначала удаление панелей, потом переименование
модулей, потом переработка компонентов, последним — `App.tsx`). Замыкает
документация. Плюс одна внеплановая задача во фронте в самом начале —
заглушка реджекта на время миграции.

> **Правка плана по ходу работы (2026-10-06).** Исходная версия этого
> раздела числила пять шагов бэкенда и не знала о двух задачах, которые
> появились в tasklist уже во время реализации. Обе утверждены человеком
> на гейте, обе закрыты; план приведён в соответствие постфактум.
>
> - **T1a (фронт, между T1 и T2): заглушить unhandled rejection.** После T1
>   четыре из шести запросов в `fetchData` (`App.tsx:56-63`) уходят на
>   удалённые маршруты, `Promise.all` реджектится, и каждые 5 минут в
>   консоли сыплется необработанный реджект. UI это не оживляет (он оживает
>   в T7) — задача закрывает только шум в консоли на всё время миграции.
>   В плане её не было потому, что план смотрел на целевое состояние, а не
>   на промежуточные: объявленное промежуточное состояние «вкладка
>   „Торговля“ пустая с T1 до T7» описано в шапке tasklist, и T1a — его
>   гигиена.
> - **T2a (бэкенд, между T2 и T3): снять `high`/`low` со снимка цены.**
>   Следствие T1, которое план не предусмотрел: единственным читателем
>   `PriceSnapshot.high`/`low` был `getATR`, удалённый в T1, после чего
>   колонки стали write-only — пишутся, не читаются никем. Схема и код
>   двинулись вместе, одной задачей, по тому же правилу, что и вердикты
>   (пункт 2 выше). Значит **DROP COLUMN-миграций в тикете две**, а не одна.

Базовый замер до работы (research): backend `npx jest` — 15 зелёных,
frontend `npx tsc -b` — чисто. Обе метрики — контрольные точки на каждом шаге.

## Контракты

### Модель БД

```prisma
model MarketSnapshot {
  id            Int      @id @default(autoincrement())
  market        String
  coinId        String
  currentPrice  Float
  previousPrice Float?
  movingAverage Float?
  ema9          Float?
  ema21         Float?
  rsi           Float?
  macdValue     Float?
  macdSignal    Float?
  macdHistogram Float?
  bbUpper       Float?
  bbMiddle      Float?
  bbLower       Float?
  bbBandwidth   Float?
  trend         String
  createdAt     DateTime @default(now())

  @@index([coinId, createdAt])
}
```

Снято: `decision`, `confidence`, `riskScore`, `expectedValue`, `reason`,
`aiReasoning` (`schema.prisma:38-43`). Плоское хранение MACD/BB сохраняется —
на нём стоит матчинг графика (`PriceChart.tsx:255-262`).

### Сервисы

```ts
// market.service.ts
captureSnapshot(dto: MarketDto): Promise<MarketSnapshotDto>  // собрать факты + записать строку
getLatest(coinId: string): Promise<MarketSnapshot | null>
getHistory(coinId: string, limit = 50): Promise<MarketSnapshot[]>

// market.comment.ts — кэш по хешу фактов, один вызов LLM на изменение
describe(snapshot: MarketSnapshotDto): Promise<string | null>

// ai.service.ts — вместо analyze(market, price, decision, reason, trend)
describeMarket(input: {
  market: string; currentPrice: number; trend: string;
  rsi: number | null; ema9: number | null; ema21: number | null;
  macdHistogram: number | null; bbBandwidth: number | null;
}): Promise<string>
```

### REST

| Метод | Путь | Отдаёт |
|---|---|---|
| `GET` | `/market/snapshot/:coinId` | последний снимок + `aiComment` |
| `GET` | `/market/history/:coinId?limit=50` | массив снимков, **без** `aiComment` |
| `POST` | `/market/refresh` | `{market, coinId}` → свежий снимок + `aiComment` |

Удаляются: `POST /analyze`, `GET /analyze/decisions/:coinId`,
`GET /wallet`, `POST /wallet/deposit`, `GET /wallet/stats`,
`GET /wallet/history`, `GET /positions`, `GET /positions/:coinId`,
`GET /positions/:coinId/open`.

### Промпт AI

Вход — только факты, без слова «решение». Системная роль: аналитик,
описывающий обстановку. Явный запрет на рекомендации — по образцу
антиразметочного запрета в `digest.service.ts:17-20`, где промпт борется
с привычками reasoning-модели.

## Поток данных

```
cron 0 */5 * * * *  ─┐
POST /market/refresh ─┴─→ MarketService.captureSnapshot(coinId, market)
                              │
                              ├─ priceService.getPrice()  ← ПИШЕТ PriceSnapshot (:41,56)
                              ├─ 8 индикаторов из PriceSnapshot (Promise.all)
                              └─ prisma.marketSnapshot.create()

GET /market/snapshot/:coinId → getLatest() → MarketComment.describe()
                                                  │
                                              hash(факты) == cached? → cached
                                                  иначе → ai.describeMarket() → cache

GET /market/history/:coinId → getHistory() ──→ график (EMA/BB) + таблица
```

Цепочка `captureSnapshot → getPrice → PriceSnapshot` сохранена намеренно:
это единственный писатель истории цен, на котором стоят все индикаторы,
график и обе следующие фичи ROADMAP.

## Trade-offs

**1. Миграция переименования пишется руками, а не генерируется.**
Prisma не умеет отличить переименование модели от «удалить одну таблицу,
создать другую» и сгенерирует DROP + CREATE. Это стоило бы всей истории
снимков, а на ней стоят линии EMA/BB на графике: `PriceSnapshot` содержит
только `price` (`types/trading.ts:1-6`), индикаторы подмешиваются из снимков
(`PriceChart.tsx:255-262`). Поэтому — `ALTER TABLE "TradeDecision" RENAME TO
"MarketSnapshot"` + `DROP COLUMN` вручную. Цена: миграцию нужно прочитать
глазами перед прогоном, автогенерации доверять нельзя.
*Отвергнуто:* `@@map("TradeDecision")` — сохранило бы данные без ручной
работы, но оставило бы в БД имя, которое врёт. Ровно та полумера, против
которой заведён тикет.

**2. Общий axios вынесен в `api/client.ts`.**
`api/news.ts:1` импортирует инстанс из `trading.ts`. Переименование файла
без этого шага роняет вкладку «Инфополе», которая по PRD не трогается.
*Отвергнуто:* оставить имя `trading.ts` — то же враньё в имени, что и в схеме.

**3. Карточка кормится отдельным эндпоинтом, а не первым элементом истории.**
Сейчас `App.tsx:70` кладёт в карточку `d[0]` из истории. После переезда
AI-комментария «на лету» историческая строка его не содержит — блок «AI»
оказался бы пустым при каждом рендере, кроме ручного обновления
(риск 8 research). Поэтому `GET /market/snapshot/:coinId` возвращает снимок
**вместе** с комментарием, а история — без него.

**4. Кэш комментария — in-memory `Map` по `coinId`.**
Как `digest.service.ts:12` и `news.translator.ts:7`. Переживает запросы,
не переживает рестарт — приемлемо: после рестарта один лишний вызов LLM
на монету. *Отвергнуто:* хранение в БД — вернуло бы поле, которое тикет
убирает.

**5. Побочный эффект `getPrice` не чиним.**
`GET /price/:coinId` пишет строку в `PriceSnapshot` на каждый запрос
(`price.service.ts:41,56`) — запись внутри геттера. Это долг, но правка
меняла бы поведение сбора данных посреди миграции. `VISION.md`: «не рефактори
и не добавляй фичи одновременно». Фиксируем как замеченное, выносим за тикет.

**6. Параметр монеты — в пути, не в query.**
PRD задаёт `GET /market/snapshot` без параметра. Беру `/:coinId` — так
устроены все существующие маршруты (`price.controller.ts:8,19`,
`analyze.controller.ts:14`).

**7. Порядок фронтовых задач подчинён компилятору.**
Сначала удаление панелей, потом переименование модулей, потом переработка
компонентов, последним `App.tsx` — так `npx tsc -b` зелёный после каждого
шага и служит оракулом. Обратный порядок дал бы три шага «красного»
компилятора, где ошибку не отличить от незавершённости.

**8. Новый тест ровно один — на кэш комментария.**
`VISION.md`: тесты только там, где есть эталон. Сборка снимка — плумбинг
без эталона, тест на неё был бы false-green. У кэша эталон есть и он
внешний по отношению к реализации: два запроса на неизменившихся фактах =
**один** вызов модели, счётчик мока даёт однозначный ответ. Математика
индикаторов уже покрыта сверкой с `technicalindicators`
(`backtest.indicators.spec.ts`) и не трогается.

## Риски

1. **Тихий обрыв сбора цен** (research, риск 1). Потеря вызова `getPrice`
   внутри `captureSnapshot` не проявится ни в логах, ни в `/health` —
   просто перестанет расти таблица. Контроль: T2a и T4 требуют после
   cron-цикла увидеть в `PriceSnapshot` **три** новые строки на границе
   пятиминутки, в порядке планировщика (bitcoin → ethereum → solana с
   интервалом ~1.5s, `price.scheduler.ts:31`), с парными строками в снимках
   рынка и тремя `[PriceScheduler] … анализ выполнен` в логе.
   *Правка 2026-10-06:* здесь стоял `count(*)` до и после. Он непригоден —
   счётчик растёт ещё и от ручного `GET /price/:coinId` (запись внутри
   геттера, trade-off 5). Негодны и `max(createdAt)`, и «появилась строка»:
   ручной GET даёт и свежую метку, и строку. Отличает cron от ручного вызова
   только подпись планировщика, поэтому оракул — она.
2. **Молчаливая потеря линий на графике** (research, риск 2). EMA/BB
   приходят из снимков через `?? null` — TypeScript пропустит. Контроль:
   глаз на графике в T8/T9.
3. **Цикл модулей** (research, риск 3). `forwardRef` в обе стороны
   (`price.module.ts:9`, `analyze.module.ts:11`). Потеря одного = падение
   Nest на старте. Контроль: приложение поднимается — критерий T4.
4. **Данные уходят навсегда** (research, риск 5). Том `postgres_data`
   именованный (`docker-compose.yml:11-12`), данные реально существуют.
   Осознано в PRD.
5. **Зелёные тесты после T3 ничего не доказывают** (research, риск 6).
   Из 15 останется 6 — все от бэктеста. Критерий «`npm run test` зелёный»
   выполним удалением файла и оракулом качества миграции не является.
   Настоящая проверка миграции — ручной прогон и глаз человека.
6. **`npm run test:e2e` сломан до нас** (research, риск 7):
   `test/app.e2e-spec.ts:19-24` ждёт `GET /` → «Hello World!», а
   `app.controller.ts:8` отдаёт только `/health`. Не трогаем, чтобы не
   принять чужую поломку за свою; отмечено в T10.
7. **Текст LLM автоматом не проверить.** Критерий 12 PRD (нет «купить /
   продать / вход / стоп») — только ревью человека на живом ответе.
