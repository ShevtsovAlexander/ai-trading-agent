- [x] **TASK-0006.3: `GET /market/candles/:coinId/history`**
  `getHistory(coinId, interval, before)` по контракту плана: окно
  `HISTORY_CHUNK + WARMUP` до `before`, ряды тем же расчётом, что
  `compute`, кэш истории, `complete`, 400 на невалидный `before`, 429 от
  стража, 502 от Binance. Тип `HistoryChunk` в `market.types.ts`.
  - Критерий готовности (jest на честном фейке Binance, образец
    `market-data.service.spec.ts:90`):
    1) ряды куска = `technicalindicators` на всех close фейка (длинный ряд)
       для тех же `t` — включая первую свечу куска;
    2) кусок `before = getSeries(...).candles[0].t` стыкуется: последняя
       свеча куска = `before − step`, дублей нет;
    3) два куска подряд (`before₂ = chunk₁.candles[0].t`) — без дыр и дублей;
    4) фейк с листингом внутри окна → `complete: true`, свечи только от
       листинга, ранние индикаторы `null`;
    5) `before` не кратен интервалу / в будущем / не число → 400 без
       запроса к Binance; вес ≥ 4800 → 429 без запроса;
    6) повторный кусок — 0 запросов (кэш);
    7) `getHistory` после своего `fetchClosedCandles` зовёт `noteWeight`:
       фейк отдаёт кусок с заголовком веса ≥ 4800 → следующий `getHistory`
       (другой `before`) — 429 и 0 вызовов фейка (фейки стража — с
       заголовком, иначе вес `null` и тест «пропустил» ложно-зелёный);
    8) Binance ответил 429/418 → вес считается исчерпанным до конца
       минуты: следующий `getHistory` в той же минуте — 429 без запроса;
    9) вес `null` (нет заголовка) → `logger.warn` (критик T2: страж
       молча выключен).
    Плюс живой: BTC 5м, 3 куска подряд — ряды = `technicalindicators` на
    свечах Binance того же отрезка (скрипт как `t8_oracle` TASK-0004);
    BTC 1д от `before` в 2018 → `complete: true`, первая свеча 2017-08-17.
  - Оракул: `technicalindicators` (эталон) + живой Binance. Мутанты:
    «без разогрева», «`t ≤ before`» — обязаны покраснеть.

**Фронт**

- [x] **TASK-0006.4: типы, API, `mergeSeries`, `evicted`, `adjoins`**
  Зеркало `HistoryChunk` и `HISTORY_CHUNK` в `types/market.ts`,
  `getHistory` в `api/market.ts`, чистые функции в `chartData.ts`:
  `mergeSeries(chunks, main)` (пропускает куски чужой монеты/интервала и
  битые — `series.length ≠ candles.length`); `evicted(prev, next)` — свечи,
  вытесненные из основного окна опросом (окно — последние N свечей, его
  левый край едет вправо, критик T4); `adjoins(prev, next)` — окна стыкуются
  (сдвиг ≤ длины окна). К экрану не подключается.
  - Критерий готовности: скрипт `npx tsx` в scratchpad, известный ответ —
    реальный сценарий: куски до левого края окна, опрос сдвинул окно на 2
    свечи → без `evicted` дыра (фиксирует находку критика), с `evicted` —
    0 дыр, значения вытесненных — из прежнего окна; 10 опросов со сдвигом
    1–2 — 0 дыр от первой свечи; сдвиг 287/288 при окне 288 — стыкуются,
    0 дыр; 289/400 — `adjoins` false, `evicted` null; опрос во время первой
    догрузки — 0 дыр; перекрытие — на совпадении `main`, без дублей;
    `series[i].t === candles[i].t`, ключ = `main`; чужой и битый кусок
    отброшены, `toChartData` не падает. Плюс живые ответы бэкенда (2 куска
    + основное окно BTC 5м) — 0 дублей, шаг `t` = интервал, кроме дыр Binance.
  - Оракул: известный ответ + живой ответ API. 8 мутантов — FAIL: без
    дедупа, без сортировки, на совпадении — кусок, `evicted` всегда null,
    `evicted` со сдвигом на 1, битый кусок не отбрасывается, `adjoins` без
    проверки стыка, `adjoins` строже на шаг.

- [x] **TASK-0006.5: `useChartHistory`, подключение в App, полоса BB по видимому**
  Хук по контракту плана; `App.tsx`: `data = useMemo(mergeSeries(chunks,
  chartShown))`. На каждом опросе того же ключа — `evicted(прежнее окно,
  новое)` добавляется к кускам всегда, а не только при загруженной истории:
  иначе опрос во время первой догрузки рвёт стык (критик T4). Без истории
  график от этого растёт вправо, левый край стоит — ряд ограничен потолком.
  `adjoins` false (окно уехало дальше своей длины — сон, простой) — история
  сбрасывается, без ложного разрыва.
  Догрузка пока по вызову из консоли/скрипта (край графика — T6).
  Потолок `MAX_BARS = 100 000`: на нём `loadMore` не грузит, хук отдаёт
  признак «потолок». Опрос (тот же ключ, левый край не сдвинулся) —
  `series.update()` правых свечей вместо `setData`; `setData` — на смену
  ключа и догрузку куска (история и опрос — разными обновлениями).
  `bandPrimitive` — только видимый логический диапазон (замер T1: обход всех
  точек — 28 мс на кадр на 100 тыс. баров, по видимому — ≤ 4 мс); идёт вместе
  с потолком, чтобы между T5 и T6 длинный ряд не тормозил прокрутку.
  - Критерий готовности (CDP): `loadMore` ×2 → на графике больше свечей,
    левее; опрос (1м, ждать) — история не стёрлась, основное окно
    обновилось, через ≥ 3 опроса на 1м между историей и окном 0 дыр (шаг
    `t` = интервал); опрос во время первой догрузки (задержка ответа куска
    через CDP) — 0 дыр; окно уехало дальше своей длины (подмена ответа
    опроса) — история сброшена; смена монеты/интервала/диапазона — история сброшена,
    нет свечей прошлой монеты и прошлого диапазона; поздний ответ куска после смены монеты не
    попадает (токен); 502/429 куска — график прежний, ошибка в состоянии;
    на 100 тыс. барах `loadMore` не шлёт запрос; опрос идёт через `update()`
    (счётчик вызовов `setData` не растёт), последняя свеча = ответ API.
  - Оракул: CDP + ответы API (внешние).
