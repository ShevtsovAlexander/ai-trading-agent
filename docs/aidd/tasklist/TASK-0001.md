    положить SQL в `prisma/migrations/<timestamp>_<name>/migration.sql` →
    `prisma migrate deploy` → `prisma generate` →

    в `_prisma_migrations`. В T2 SQL сгенерирован машиной и совпал, но в T4
    он пишется руками (`ALTER TABLE ... RENAME` **плюс** `ALTER INDEX`).

## Что осталось за рамками (замечено, не делается)

- **Побочный эффект `getPrice`**: `GET /price/:coinId` пишет строку в
  `PriceSnapshot` на каждый вызов (`price.service.ts:41,56`). Долг замечен,

- **`npm run test:e2e` сломан до миграции**: `test/app.e2e-spec.ts:19-24`
  ждёт `GET /` → «Hello World!», а `app.controller.ts:8` отдаёт только
  `/health`. Не трогаем, чтобы не смешать чужую поломку со своей.
- **`NewsPanel.tsx:21-32` — `try/finally` без `catch`.** Третья точка того же
  дефекта, что чинился в T1a: при отказе `/news` или `/news/digest` панель
  поставит `loading=false` в `finally` и покажет пустую ленту без индикации
  ошибки. Дефект **не наш** — он есть в HEAD до тикета, и держится сейчас
  только на том, что оба маршрута отвечают 200. Не чиним: PRD прямо выводит
  «Инфополе» за скоуп. Отдельный тикет; правило из подпункта T6 на него
  просится, но это уже другая работа.
- **`npm run start:prod` нерабочий**: `package.json:17` зовёт `node dist/main`,
  а `nest build` кладёт точку входа в `dist/src/main.js` — из-за
  `backend/prisma.config.ts` в корне пакета `rootDir` поднимается на уровень
  выше. `node dist/main` падает `MODULE_NOT_FOUND`. Дефект **не наш** — он из
  начального коммита `310528e`. Не чиним: к демонтажу торгового ядра
  отношения не имеет, отдельный тикет (просится в компанию к `.env.example`).
  **Следствие для этого тикета:** формулировка «приложение стартует» в
  критериях закрывается ручным `node dist/src/main`, поэтому в T4 команда
  названа явно. Пока скрипт сломан, «приложение стартует» через
  `start:prod` — латентный false-green: критерий ссылался бы на путь,
  которым приложение не запускается ни у агента, ни у человека.
- **EMA, RSI и MACD считаются по САМЫМ СТАРЫМ данным и не меняются
  месяцами.** `price.service.ts:104` (`getEMA`), `:125` (`getRSI`),
  `:152` (`getMACD`) делают `orderBy: { createdAt: 'asc' }` с фиксированным
  `take` — то есть берут начало истории, а не свежие строки.
  `getBollingerBands` (`:209`), `getMovingAverage` (`:16`) и `getTrend`
  (`:72`) берут `desc` и работают верно. Замер в живой БД (bitcoin, 159

  Те же значения стоят в примере ответа в `backend/CLAUDE.md`, то есть
  с начального коммита. Дефект **не наш**, старше тикета.
  Не чиним здесь: `asc` → `desc` меняет все числа на дашборде, и делать это
  посреди миграции нельзя — отдельный тикет, **первый после тикета**:
