## Как устроены смежные части

### Выборки в PriceService — образец правильного и неправильного

Верно (свежие строки):
```ts
// price.service.ts:207-211 — getBollingerBands
orderBy: { createdAt: 'desc' },
take: period,
```
`getBollingerBands` порядок не важен — среднее и дисперсия симметричны.

Верно, с разворотом в хронологию — **единственный готовый образец
`desc` + reverse в сервисе**:
```ts
// price.service.ts:70-78 — getTrend
orderBy: { createdAt: 'desc' },
take: points,
...
const prices = snapshots.reverse().map((s) => s.price);
```

Неверно:
```ts
// price.service.ts:102-106 — getEMA
orderBy: { createdAt: 'asc' },
take: period * 3, // берём больше данных для точности
```

### RSI — второй дефект, не только порядок
```ts
// price.service.ts:131-138
const prices = snapshots.map((s) => s.price);
const changes = prices.slice(1).map((p, i) => p - prices[i]);
...
const avgGain = gains.slice(0, period).reduce((a, b) => a + b, 0) / period;
const avgLoss = losses.slice(0, period).reduce((a, b) => a + b, 0) / period;
```
`take: period + 10` = 24 цены → 23 дельты, используются первые 14.
Последние 9 дельт выбрасываются. Для сравнения, бэктест-версия берёт
окно, **заканчивающееся** на текущем индексе:
```ts
// backtest.service.ts:335-336
for (let i = period; i < prices.length; i++) {
  const slice = prices.slice(i - period, i + 1); // period+1 цен = period дельт
```
Комментарий `backtest.service.ts:331` («Алгоритм идентичен getRSI в
price.service.ts») неточен: формула средних одна, окно — разное.

### EMA — усечённая история
`getEMA` сидирует SMA по первым `period` точкам окна из `period*3`
(`price.service.ts:105`, `:113`). Значение зависит от размера окна и
не совпадёт с EMA по всей истории (как считает `technicalindicators`)
точно — только приближённо. Это свойство текущего кода, не дефект
порядка.

### MACD в PriceService
Выравнивание в `price.service.ts:176-178`: `calcEMA` возвращает массив
от индекса `period-1`, поэтому `ema12.length - ema26.length = 14`.
Арифметика верна. Бэктест-версия (`backtest.service.ts:354-385`)
держит массивы полной длины с NaN-префиксом — устроено иначе.

### Кто вызывает индикаторы
```ts
// market.service.ts:28-38
] = await Promise.all([
  this.priceService.getPrice(dto.coinId),      // пишет PriceSnapshot (:54)
  this.priceService.getPreviousPrice(dto.coinId), // skip: 1 (:63) — «пропускаем текущую»
  this.priceService.getTrend(dto.coinId),
  ...
  this.priceService.getEMA(dto.coinId, 9),
```
`getPreviousPrice` (`price.service.ts:59-67`) предполагает, что текущая
строка уже записана (`skip: 1`), но вызывается параллельно с записью.
При `asc` гонка не влияла на мёртвые EMA/RSI/MACD; после `desc` она
определяет, попадает ли текущая цена в окно.

`captureSnapshot` зовут: крон `price.scheduler.ts:15-25` (каждые 5 минут,
три монеты подряд с паузой 1.5 с, `:30`) и `POST /market/refresh`
(`market.controller.ts:13-15`, кнопка обновления на фронте).

### Источник строк PriceSnapshot
Пишет только `getPrice` (`price.service.ts:41`, `:54`). Вызывают:
`captureSnapshot` (выше) и `GET /price/:coinId` (`price.controller.ts:8-10`).
Значит, ручной вызов `GET /price` вставляет строку вне 5-минутной сетки —
окна индикаторов в «точках» перестают быть окнами во времени.
Схема: `PriceSnapshot` с индексом `@@index([coinId, createdAt])`
(`backend/prisma/schema.prisma:9-16`) — `orderBy desc` + `take` по индексу.

### Как график получает данные

### График — что нарисовано на деле
```tsx
// PriceChart.tsx:285-307
<Area dataKey="bbUpper" stroke="#334155" fill="none" strokeDasharray="3 3" .../>
<Area dataKey="bbLower" stroke="#334155" fill="#1e293b" fillOpacity={0.3} .../>
```

Ни у одной `Area` нет `connectNulls`; у обеих `Line` EMA — есть
(`:317`, `:328`). На точках без снимка BB рвётся на куски, EMA
протягивается прямой через дыру.

```tsx
// PriceChart.tsx:223 — готовая полоса, не используется
bbRange: h.snapshot ? [h.snapshot.bbLower, h.snapshot.bbUpper] : null,
```
Если снимок есть, но `bbLower == null` (истории < 20 точек,
`price.service.ts:213`), получится `[null, null]`, а не `null`.


## Риски изменения

1. **False-green по оракулу (критично для критерия 2 PRD).**
   `backtest.indicators.spec.ts` проходит независимо от `PriceService` —
   он его не импортирует (`:10`). Зелёный `npm run test` после правки
   ничего не скажет о починке.
2. **RSI: оракул всегда зелёный.** `backtest.indicators.spec.ts:108-110` —
   `expect(...).toBeGreaterThanOrEqual(0)`, комментарий «всегда проходит».
   Сам тест печатает, что `technicalindicators` использует сглаживание
   Уайлдера, а код — простое среднее (`:102-103`). Значит, даже
   правильно развёрнутый `getRSI` не совпадёт с эталоном: это другая
   формула RSI. Решение «какую формулу считать правильной» — вне
   этого research.
3. **Только смена `asc` → `desc` без разворота сломает EMA/MACD
   тихо**: рекуррентная формула пойдёт от свежей точки к старой, и
   значения будут правдоподобными, но неверными. PRD это уже отмечает
   (критерий 1).
4. **Гонка `getPrice` ↔ `get*`** (`market.service.ts:28-38`) — после
   починки индикаторы будут то включать текущую цену, то нет.
   `getPreviousPrice` с `skip: 1` (`price.service.ts:63`) страдает
   тем же уже сейчас.
5. **Дыры в данных.** Окно EMA21 = 63 строки, MACD = 78 строк
   (`price.service.ts:105`, `:153`). PRD фиксирует разрывы до 62 дней —
   после рестарта бэкенда окно склеит цены через дыру. Это не дефект
   порядка, но первые снимки после простоя будут считаться по смеси
   старых и новых цен.
6. **Производительность графика.** `matchSnapshots` — перебор
   `history × snapshots` (`PriceChart.tsx:124-135`); на «3мес» это до
   25920 × 25920. Сейчас данных мало (PRD: 172 точки), риск не
   проявляется.
7. **Смена оси X на временную** (пункт 4 PRD) меняет `tickFormatter`
   (`PriceChart.tsx:192-198`) и тултип (`:166-170`) — они получают
   строку `createdAt`.
